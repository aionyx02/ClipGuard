# S4 macOS：剪貼簿監聽、密碼管理器標記、前景 App、攔截 Cmd+V

- 日期：2026-11-24　平台：macOS（Darwin 27.2，Apple Silicon）　終端機：Ghostty
- 版本：Rust 1.100（rustup stable）、`objc2` 0.6.5、`objc2-foundation` / `objc2-app-kit` / `objc2-core-graphics` / `objc2-core-foundation` / `objc2-application-services` 0.3.2
- Spike 程式放在暫存資料夾，不合併：單一執行檔 `pw-s4`，子命令有 `types`、`poll`、`stress`、`perms`、`tap`。**程式只印變動次數、類型名稱、文字長度和前景 App，不印任何剪貼簿內容。**

## 結論：可行

| 項目 | 結果 |
|---|---|
| 輪詢 `NSPasteboard.changeCount`（250 ms） | ✅ 人工複製 4 次都偵測到 |
| 密碼管理器標記（Concealed / Transient / AutoGenerated） | ✅ 用私有具名 pasteboard 寫入，三種都偵測到；從真的密碼管理器複製時也偵測到 `ConcealedType`，而且**完全沒讀文字** |
| 前景 App（`NSWorkspace.frontmostApplication`） | ✅ 拿得到名稱和 Bundle ID |
| CGEventTap 攔截 Cmd+V（active tap，回傳 NULL） | ✅ 在 Sublime Text 按兩次 Cmd+V，兩次都被吞掉、沒有貼上 |
| 閒置成本 | 每次輪詢 27 µs，30 秒 CPU 時間約 0，RSS 約 9 MB |

## 數據

### `autoreleasepool` 一定要包

每次迭代會呼叫 `changeCount`、`types()`、`stringForType(.string).length`、`frontmostApplication`：

| 迭代次數 | 有 `autoreleasepool` | 沒有 `autoreleasepool` |
|---|---|---|
| 200,000 | 16 MB | 32 MB |
| 600,000 | 16 MB | 64 MB |
| 1,200,000 | **16 MB** | **111 MB**（線性成長） |

只呼叫 `changeCount` 和 `types()` 時，兩者都不會漏，因為 objc2 拿到的是 retained 的回傳值。但 `stringForType`、`NSWorkspace` 這類呼叫會產生 autoreleased 物件。沒包的話，每次約漏 86 bytes，以每秒 4 次輪詢估算，**一天約 30 MB**。規格書「每次輪詢都包在 `autoreleasepool`」是對的，而且要包住整個迭代，不能只包讀取那一段。

### 權限

`AXIsProcessTrusted`、`CGPreflightListenEventAccess`、`CGPreflightPostEventAccess` 都是 true，因為這台機器的 Ghostty 本來就有「輔助使用」和「輸入監控」權限，而從終端機執行的程式會繼承終端機的權限。

- **active tap**（能吞掉按鍵）需要「輔助使用」；listen-only 只需要「輸入監控」。
- **還沒驗證**：一個全新、沒有任何權限的 App bundle（正式的 Tauri 版）第一次請求授權的流程。`CGRequestListenEventAccess()` 會跳系統對話框，但「輔助使用」只能引導使用者到系統設定自己打開，而且多數情況要重開 App 才生效。Phase 4 要在乾淨的 macOS 使用者帳號上實測。

## 發現

1. **Chrome 會在剪貼簿附上來源網址**：複製網頁內容時，types 裡有 `org.chromium.source-url`（還有 `org.chromium.internal.source-rfh-token`）。**桌面版不靠擴充功能，也能知道內容來自哪個網站**，可以直接拿來做 Phase 1 的情境加權（`Context.source`）。Safari、Firefox、Arc、Edge 有沒有類似的 type 還沒測。這是網址，屬於隱私資料，讀了之後只能拿來判斷，不能寫進 log。
2. **「前景 App」不等於「來源 App」**：人工測試時，4 次複製偵測到的前景 App 都是 Ghostty，因為輪詢有最多 250 ms 的延遲，而且使用者常常複製完就切換視窗。正式版的建議：
   - 前景 App 改用 `NSWorkspaceDidActivateApplicationNotification` 持續追蹤，剪貼簿變動時取「變動前最後一個前景 App」。
   - 有 `org.chromium.source-url` 這類 metadata 時，以 metadata 為準。
3. **有剪貼簿變動的那幾次輪詢比較貴**：人工測試平均 263 µs/poll，因為那幾次要讀文字和查前景 App。閒置時是 27 µs，影響可以忽略。
4. **tap 被系統停用**：系統覺得 callback 太慢或使用者操作時，會送出 `TapDisabledByTimeout` / `TapDisabledByUserInput`，spike 已經實作「收到就重新啟用」。正式版的 callback 只能做極少的事，判斷結果要先算好放在共用狀態裡，callback 只負責查表（同 Windows 版 §5.3 的 hook 安全原則）。

## 建議做法（Phase 4）

- `crates/platform/src/macos/`：
  - `ClipboardMonitor`：獨立執行緒，250 ms 輪詢，整個迭代包在 `autoreleasepool` 裡；先看 types，有密碼管理器標記就略過，不讀文字；再讀 `public.utf8-plain-text` 和來源 metadata。
  - `ActiveWindowProvider`：訂閱 `NSWorkspace` 的 activate 通知，維護最近的前景 App 紀錄。
  - `PasteInterceptor`：CGEventTap（active），callback 只查「目前剪貼簿是否要攔」這個旗標；被停用時自動重啟；沒有權限時降級成只通知、不攔截，並在 UI 引導使用者授權。
  - `ClipboardWriter`：`clearContents()` 後只寫純文字，寫入的內容雜湊記進自我寫入防迴圈的快取。
- 單元測試用私有具名 pasteboard（`NSPasteboard::pasteboardWithName`），CI 的 macOS runner 也能跑，不會動到系統剪貼簿。

## 待決問題

1. 其他瀏覽器有沒有來源網址 metadata（Safari、Firefox、Arc、Edge）。
2. 全新 App bundle 的授權流程，以及沒有權限時的使用體驗（Phase 4 用乾淨帳號實測）。
3. macOS 新版本如果加入「App 讀剪貼簿要經過使用者同意」的機制（iOS 已經有），背景輪詢會受影響。要追蹤 Apple 的政策。
